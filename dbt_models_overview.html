Defence dbt Projects: Model Documentation

Overview

The dbt/ folder holds seven dbt projects for the Defence channel, all on Amazon Redshift. Each project deploys and runs on its own. This page documents them one at a time. Only defence_agent_master is covered so far.

1. defence_agent_master

Purpose. Builds the agent master, a dimension table with one row per sales person (agent) or leader in the Defence channel for the reporting month. Each row carries the person's role level and the reporting chain above them (RM, OH, AH, RH, VH, CH), plus zone, tenure and status. The KPI tables (for example BSC, health and GO/HO movement) carry the same hierarchy columns so KPIs can be rolled up the chain.

KPIs created by this project: none. It produces no numeric KPI. The only derived measure is vintage (tenure in months). The KPI-bearing tables belong to the other six projects.

dbt project name: rrd_defence  |  profile: rrd_dbt_redshift  |  target: Redshift

Models, one by one

Staging layer

1. stg_rrd_defence_agents view defence_int

  • Grain: one row per agent per reporting month.
  • Sources: m1_agent_as_on_date, m1_agent_as_on_date_hist.
  • Logic: two CTEs (current and history) select the same 17 columns. Each filters month = get_reporting_date('month') and status in ('Active','Suspended','Terminated'). A plain UNION combines them and removes duplicates. This lets a past month be re-run from the history table.

2. stg_rrd_defence_desig_roles view defence_int

  • Grain: one row per designation code.
  • Source: setup_defence_designation_roles.
  • Logic: pass-through of desig_code, desig_desc, starting_id_role_master_flag. The last column is the key business rule. It says which hierarchy level (Agent or RM) a designation belongs to.

3. stg_rrd_defence_geo_hier view defence_int

  • Grain: one row per GO code per effective month.
  • Sources: mf_defence_geo_hier_lvl, mf_defence_geo_hier_lvl_hist.
  • Logic: same current plus history pattern. Filter: effective_month = get_reporting_date('month'), then UNION.

Intermediate layer

4. int_rrd_defence_agent_base view defence_int

  • Grain: one row per agent or RM.
  • Inputs: stg_rrd_defence_agents, stg_rrd_defence_desig_roles, stg_rrd_defence_geo_hier.
  • Logic:
    1. Join agents to designations on role_code = desig_code. Keep only designations whose starting_id_role_master_flag is Agent or RM. This sets master_flag.
    2. Inner join to the geo hierarchy on go = go_code. Agents whose GO is not in the hierarchy are dropped.
    3. role_code_desc = desig_desc.
    4. rm_id = reporting_to_sm_id when the person is an Agent, otherwise null. An agent's RM is their direct supervisor.
    5. supervisor_id = reporting_to_sm_id.
    6. vintage = whole months between the first of the reporting-date month and the first of the join-date month.

5. int_rrd_defence_leaders view defence_int

  • Grain: one row per distinct leader ID per level.
  • Inputs: stg_rrd_defence_geo_hier, stg_rrd_defence_agents.
  • Logic: leaders do not come from designations. They come from the geo hierarchy. Five SELECT DISTINCTs are unioned:

6. int_rrd_defence_combined view defence_int

  • Grain: one row per person (agent, RM, OH, AH, RH, VH, CH).
  • Logic: UNION ALL of agent_base and leaders on 12 common columns: agent_id, agent_name, master_flag, join_date, status, role, role_code, role_code_desc, rm_id, supervisor_id, go_code, vintage.

Mart layer

7. rrd_agent_master_defense (file name) → table defence_mart.rrd_agent_master_defence incremental, append

  • Grain: one row per person for the reporting month. The table holds only the current month.
  • Refresh pattern: pre_hook runs delete from defence_mart.rrd_agent_master_defence, then the model appends. Each run is a full replace of the table.
  • Inputs: int_rrd_defence_combined, stg_rrd_defence_geo_hier, stg_rrd_defence_agents, stg_rrd_defence_desig_roles.
  • Logic:
    1. Left join combined to the geo hierarchy on go_code to get the chain of leaders above the person's GO.
    2. month_id = reporting month (get_reporting_date('month')), etl_insert_date = current_timestamp.
    3. channel and sub_channel are hard-coded 'DEFENCE'.
    4. Hierarchy columns are filled only for levels above the person's own level. A person does not get their own ID as a parent:

  • rm_supervisors CTE: agent IDs whose designation maps to starting_id_role_master_flag = 'RM'. It decides rm1_id.
  • post_hook: after the insert, supervisor_id is overwritten with reporting_to_sm_id from stg_rrd_defence_agents for every agent_id found there. For leaders, the geo-derived supervisor is replaced by the supervisor in the agent snapshot when one exists.

8. rrd_agent_master_defence_hist incremental, append defence_mart

  • Grain: one row per person per month-end.
  • Inputs: defence_date_master, rrd_agent_master_defence (current master, via source).
  • Logic: a month-end check counts rows in defence_date_master where month_end_flag = 'Y'. The model cross joins that count and returns all master rows only if the count is above zero. It snapshots the master only on month-end runs.
  • Idempotency: pre_hook first deletes rows from the hist table where month_id equals the current tmast_month_id. A month-end re-run replaces that month rather than duplicating it. Other months are never touched.
  • Dependency: it reads the master through source(), not ref(), so dbt does not know it must run after rrd_agent_master_defense.

Run and deploy

  • dbt_run.sh loads env.properties (linked to config/uat.properties or prod.properties), activates the virtualenv, reads Redshift credentials from AWS Secrets Manager (ap-south-1) into REDSHIFT_* environment variables, runs dbt run, renames the log, uploads it to s3://<logs bucket>/dbt/YYYY/MM/DD/defence_agent_master/, and exits non-zero if dbt failed.
  • Back-fill example: dbt run --vars '{reporting_month: "202410", reporting_date: "2024-10-31"}'

Observations from the code

  1. Status filter. Staging keeps Terminated agents, but assert_status_filter expects only Active or Suspended. The test fails whenever terminated agents exist in the month.
  2. Missing macro. assert_audit_metadata calls get_reporting_month(), which is not defined in macros/. The existing macro is get_reporting_date('month').
  3. DDL versus model. The mart selects status, but the rrd_agent_master_defence DDL in DEFENCE DDL.txt has no status column. Check the deployed table.
  4. Run order. The hist model reads the master through source(), so dbt does not order it after the master model. If both run in one dbt run, hist may copy the previous month's master.
  5. Master is a full replace. The pre_hook deletes the whole master table before each insert. A failed insert leaves the table empty until the next successful run.
  6. Unused macro. get_date_vars is not called in this project.
  7. Hard-coded schema. The pre_hook SQL strings use defence_mart. literally.
