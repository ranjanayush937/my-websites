1. defence_agent_master

Purpose. Builds the agent master, a dimension table with one row per sales person (agent) or leader in the Defence channel for the reporting month. Each row carries the person's role level and the reporting chain above them (RM, OH, AH, RH, VH, CH), plus zone, tenure and status. The KPI tables (for example BSC, health and GO/HO movement) carry the same hierarchy columns so KPIs can be rolled up the chain.

KPIs created by this project: none. It produces no numeric KPI. The only derived measure is vintage (tenure in months). The KPI-bearing tables belong to the other six projects.

Models, one by one

Staging layer

1. stg_rrd_defence_agents view defence_int

  • Grain: one row per agent per reporting month.
  • Sources: m1_agent_as_on_date, m1_agent_as_on_date_hist.
  • Logic: two CTEs (current and history) select the same 17 columns. Each filters month = get_reporting_date('month') and status in ('Active','Suspended','Terminated'). A plain UNION combines them and removes duplicates. This lets a past month be re-run from the history table.

2. stg_rrd_defence_desig_roles view defence_int

  • Grain: one row per designation code.
  • Source: setup_defence_designation_roles.
  • Logic: pass-through of desig_code, desig_desc, starting_id_role_master_flag. The last column is the key business rule. It says which hierarchy level (Agent or RM) a designation belongs to.

  • Sources: mf_defence_geo_hier_lvl, mf_defence_geo_hier_lvl_hist.
  • Logic: same current plus history pattern. Filter: effective_month = get_reporting_date('month'), then UNION.

Intermediate layer

4. int_rrd_defence_agent_base view defence_int

  • Grain: one row per agent or RM.
  • Inputs: stg_rrd_defence_agents, stg_rrd_defence_desig_roles, stg_rrd_defence_geo_hier.
  • Logic:
    1. Join agents to designations on role_code = desig_code. Keep only designations whose starting_id_role_master_flag is Agent or RM. This sets master_flag.

8. rrd_agent_master_defence_hist incremental, append defence_mart

  • Grain: one row per person per month-end.
  • Inputs: defence_date_master, rrd_agent_master_defence (current master, via source).
  • Logic: a month-end check counts rows in defence_date_master where month_end_flag = 'Y'. The model cross joins that count and returns all master rows only if the count is above zero. It snapshots the master only on month-end runs.
  • Idempotency: pre_hook first deletes rows from the hist table where month_id equals the current tmast_month_id. A month-end re-run replaces that month rather than duplicating it. Other months are never touched.
  • Dependency: it reads the master through source(), not ref(), so dbt does not know it must run after rrd_agent_master_defense.

Run and deploy

  • dbt_run.sh loads env.properties (linked to config/uat.properties or prod.properties), activates the virtualenv, reads Redshift credentials from AWS Secrets Manager (ap-south-1) into REDSHIFT_* environment variables, runs dbt run, renames the log, uploads it to s3://<logs bucket>/dbt/YYYY/MM/DD/defence_agent_master/, and exits non-zero if dbt failed.

Observations from the code

  1. Status filter. Staging keeps Terminated agents, but assert_status_filter expects only Active or Suspended. The test fails whenever terminated agents exist in the month.
  2. Missing macro. assert_audit_metadata calls get_reporting_month(), which is not defined in macros/. The existing macro is get_reporting_date('month').
  3. DDL versus model. The mart selects status, but the rrd_agent_master_defence DDL in DEFENCE DDL.txt has no status column. Check the deployed table.
  4. Run order. The hist model reads the master through source(), so dbt does not order it after the master model. If both run in one dbt run, hist may copy the previous month's master.
  5. Master is a full replace. The pre_hook deletes the whole master table before each insert. A failed insert leaves the table empty until the next successful run.
  6. Unused macro. get_date_vars is not called in this project.
  7. Hard-coded schema. The pre_hook SQL strings use defence_mart. literally.

2. defence_plan_wise

Purpose. Publishes the plan (target) figures that the Defence channel sets for each person, for the current month (MTD), the current quarter (QTD) and the current fiscal year (YTD). There are two plan populations, so there are two mart tables: producer-level plan for RMs, and geography-level plan for OH and above, rolled up OH → AH → RH → VH → CH.

KPIs created: six plan measures (plan_value, plan_afyp, plan_mfyp, plan_man_month, plan_lecture, plan_lead_target). They are targets copied from source plan tables and summed. This project does not compute achievement. Actuals and achievement % live in other projects (for example the BSC table has lecture_plan and lead_target).

Models, one by one

Staging layer

1. stg_defence_plan_agent_master table defence_int

  • Grain: one row per person for the current month.
  • Logic: reads rrd_agent_master_defence and rrd_agent_master_defence_hist. Both are filtered to month_id = curr_mth_id from get_date_vars(), trimmed on every text column, and combined with UNION. The full hierarchy (rm, rm1, oh, ah, rh, vh, ch) and master_flag are carried through. A dedupe step (row_number on latest etl_insert_date) is commented out.

2. stg_defence_plan_geo table defence_int

  • Grain: one row per office per month. All months are kept, which QTD and YTD need.
  • Logic: current plus hist, UNION. Drops rows where month_id or office_code is null. Text columns are trimmed. The five plan columns are cast safely to numeric(34,4): coalesce(nullif(regexp_replace(trim(col::varchar), '[^0-9.]', ''), ''), '0')::numeric(34,4). This strips non-numeric characters (commas, currency signs, text) and turns empty results into 0, so it never fails on bad data. Side effect: a negative value loses its sign, because - is stripped.
  • Renames: afyp → plan_afyp, mfyp → plan_mfyp, man_month → plan_man_month, lecture → plan_lecture, lead_target → plan_lead_target.

3. stg_defence_plan_producer table defence_int

  • Grain: one row per RM per month. All months are kept.
  • Logic: current plus hist, UNION. Drops null month_id or agent_id. Same safe numeric cast. Renames go → go_code, plan → plan_value, lecture → plan_lecture, lead_target → plan_lead_target. It also keeps role, role_code, status, vintage and join_date (as text) as given in the plan source.

4. stg_defence_plan_geo_hier table defence_int

  • Grain: distinct (RH, VH, CH) combinations for the current month.
  • Logic: current plus hist of mf_defence_geo_hier_lvl, filtered to effective_month = curr_mth_id and non-null RH, then UNION. No other model uses it. The marts take the hierarchy from the agent master instead.

Intermediate layer

5. int_defence_plan_geo_hierarchy table defence_int

  • Grain: one row per office per month, expected.
  • Logic: inner join stg_defence_plan_geo (g) to stg_defence_plan_agent_master filtered to master_flag = 'OH' (m), on g.office_code = m.go_code. The OH person for that office supplies oh_id (their own agent_id) and the parents ah_id, rh_id, vh_id, ch_id. zone is the master zone, falling back to the plan zone. Offices with no OH in the master are dropped by the inner join.
  • Caveat: the comment says one OH per office, but the rn = 1 filter is commented out. If two OH rows share a go_code, the office plan is counted twice.

6. int_defence_plan_producer_hierarchy table defence_int

  • Grain: one row per RM per month.
  • Logic: left join stg_defence_plan_producer to stg_defence_plan_agent_master on agent_id. It attaches name, master_flag, role description, rm_id, rm1_id, oh/ah/rh/vh/ch and zone. A producer missing from the master stays in with null hierarchy. The dedupe is commented out here too, so a duplicate master row would double the plan.

Mart layer

Period tagging (both marts). get_date_vars() returns the latest row of defence_date_master. Each intermediate row is copied once for every period it belongs to, and time_dimension says which:

time_dimensionRows included (source month_id)Meaning
MTDequal to the current monthPlan for the current month
QTDbetween quarter start month and quarter end monthSum of monthly plans for the whole current quarter
YTDbetween fiscal year start month and fiscal year end monthSum of monthly plans for the whole fiscal year

All output rows are stamped with month_id = current month (period_month_id), so a QTD or YTD row is identified by the current month, not the source month. QTD and YTD use the quarter and fiscal-year end as the upper bound, so they include planned months after the current month. They are the plan for the whole period, not the plan up to today.

7. mart_defence_plan_wise_dtl table defence_mart   sort: time_dimension, month_id   dist: agent_id

  • Grain: one row per RM (agent_id) per time_dimension.
  • Source: int_defence_plan_producer_hierarchy.
  • Logic: build the MTD, QTD and YTD sets, UNION ALL them, then group by time_dimension, period_month_id, agent_id. Descriptive columns use max(). KPIs use sum() across the months in the period. There is no rollup to higher levels.
  • KPIs: plan_value, plan_lecture, plan_lead_target.

  • KPIs: plan_afyp, plan_mfyp, plan_man_month, plan_lecture, plan_lead_target.

9. mart_defence_plan_wise_dtl_hist and 10. mart_defence_plan_geo_dtl_hist incremental, append defence_mart

  • Grain: same as the mart each one snapshots.
  • Logic: returns the rows of its mart where month_id equals the current month, only if month_end_flag = 'Y' on the latest date-master row. On other days it returns no rows and appends nothing.
  • Idempotency: a pre_hook deletes from {{ this }} the rows for the current month, only when the month-end flag is 'Y'. A month-end re-run replaces that month's snapshot. Earlier months stay.
  • These use ref() to their mart, so dbt orders them correctly. The hist model in defence_agent_master does not.

3. defence_agent_sales

Purpose. This is the main sales scoreboard for the Defence channel. For every person (Agent, RM, OH, AH, RH, VH, CH) it builds one row per period (MTD, QTD, YTD) with 148 KPIs. The KPIs follow a policy through its life: Applied (proposal sent), WIP (being processed), Hub Hold (held at the hub), Paid (premium received) and Leakage (policies lost after applying). Plans (targets) are placed beside actuals so the table can show achievement %.

Output table: defence_mart.rrd_defence_sales (current month) and rrd_defence_sales_hist (month-end snapshots).
Business impact. Leaders use this table to see, at every level, how much business the team applied for, how much turned into paid premium, how much is stuck, how much was lost, and how that compares with target. A wrong number here changes how teams are ranked and, most likely, how they are rewarded. This is why the CEIP and CRPF credit rules in this project matter: they decide which office and which RM get credit for a sale.

Models, one by one

A. Reference data (who sits where)

1. int_go_base table

  • What it does: lists every GO (office) code with the leaders above it: OH, AH (and AH office), RH (and RH office), VH (and head office), CH.
  • Logic: stacks mf_defence_geo_hier_lvl and its hist table for the current month. Uses UNION and DISTINCT to remove repeats.
  • Business impact: this is also a gate. Every policy table below inner-joins to it, so a policy written under a GO code that is missing from the hierarchy is dropped from every KPI.

2. int_hierarchy_base table

  • What it does: for each agent, finds the RM they report to (starting_id).
  • Logic: stacks hierarchy_agency_all and hierarchy_agency_hist, joins to the designation setup table on starting_desig = desig_code, keeps current month and keeps only designations flagged RM.
  • Business impact: this decides which RM's team a policy counts for. An agent with no row here has no RM, so the sale is not counted in any RM total (it still counts for the agent and for OH and above).

C. CEIP and CRPF rules (who gets credit)

11. rrd_denfence_ceip_mapping incremental, append

  • What it does: links each policy number to its CEIP campaign.
  • Logic: joins the S3 sourcing and application tables on _id and left joins the additional flags. Drops deleted records (operation = 'D'). For each policy number (case-insensitive) keeps only the latest record by updatedtime. Drops rows with a blank campaignid. Stamps the current month_id. A pre_hook deletes the current month's rows first, so a re-run does not duplicate.
  • Note: the source tables carry no month, so a run for an earlier month still reads today's S3 data.

12. int_defence_ceip_adjustment table

  • What it does: the final list of CEIP policies with their campaign ID.
  • Logic: takes policy and campaign from the CEIP adjustment dump (current + hist, current month) and full outer joins to the mapping above on policy number. A policy that appears on either side is kept. When both have it, the adjustment dump's campaign wins (COALESCE puts it first).

13. rrd_defence_ceip_crpf_branch table

  • What it does: finds agents who moved into or out of the CRPF offices (GO ADLU2 or ADGW2).
  • Logic: stacks the agent snapshot and hist, uses LAG(go) to get the previous GO, and keeps rows where the GO changed, the new GO is an active office, and exactly one of the old or new GO is a CRPF office.
  • Check this: both snapshots are filtered to the current month before LAG runs, so each agent normally has one row and no "previous" GO. The model may return few or no rows. Please test it on real data (see observations).

D. Putting all policies in one place

14. int_sales_agg_mart_lvl table

  • Grain: one row per policy per stage (mart_name).
  • Logic: UNION ALL of PAID_WPC, APPLIED, PAID, WIP, HUBHOLD, LEAKAGE and the four pre-issuance stages, all in one column layout. Then the product_split macro creates five extra columns for each of seven measures (NOP, MFYP, adj MFYP, AFYP, adj AFYP, employee WFYP, seller WFYP). For example protection_pol_afyp holds AFYP only when the product category is PROTECTION. That is 35 split columns.
  • Business impact: this one table lets every later KPI be a simple filter on mart_name and product_category. It is also the reason the product-mix KPIs add up to the total.

15. int_sales_agg_mart_lvl_ceip table

  • What it does: moves CEIP sales to the right RM and office.
  • A policy counts as CEIP only when both are true: (a) it is in int_defence_ceip_adjustment, and (b) its writing agent is a CEIP Agent in the current agent snapshot.
  • New RM (rm_derived): the policy's campaignid. If that campaign ID is in the CRPF branch list, the value is the text TBH instead.
  • New GO (wr_go_code_derived): first choice ADLU2 when the campaign ID matched the CRPF list. Second choice the GO of the campaign agent in the agent master. Third choice the writing agent's own GO from the snapshot. Non-CEIP policies keep their original GO. The original is always kept in wr_go_code_main.
  • Business impact: a CEIP agent sells under a campaign run by an RM. With this rule the sale is counted in that RM's team and that RM's office hierarchy, not in the CEIP agent's own office. This directly changes OH, AH, RH, VH and CH totals.

16. int_sales_agg_with_hierarchy incremental, append

  • What it does: attaches the reporting chain to every policy row.
  • Logic: takes the CEIP model. wr_go_code becomes the derived GO. Joins int_hierarchy_base on agent and month for the RM (starting_id; replaced by rm_derived when there is one). Joins int_go_base on the derived GO for OH, AH, RH, VH and CH and their offices. A pre_hook deletes the current month before appending.
  • All joins are left joins, so no policy row is lost here.

J. Mart layer

31. rrd_defence_sales incremental, append defence_mart

  • Grain: one row per person, per time_dimension (MTD, QTD, YTD), for the current month. Persons are Agent, RM, OH, AH, RH, VH and CH.
  • Refresh: a pre_hook runs TRUNCATE TABLE, then the model appends. Each run replaces the full table. Table grants stay in place because the table is not dropped.
  • Logic: reads int_defence_sales_hier_rollup and applies the KPI formulas. Actuals are wrapped in COALESCE(..., 0). Ratios use NULLIF(denominator, 0) and return null when the denominator is zero. The only exceptions are KPIs 13 and 33, which return 0.
  • Plan joins:
    • Agent and RM rows: producer plan, matched on agent, time_dimension and master_flag.
    • OH to CH rows: geo plan, matched on agent, time_dimension and hierarchy level.
  • Two helper tables inside the model:
    • rm_wfyp_count: for each OH, AH, RH, VH and CH, the number of RMs under them whose paid non-ULIP WFYP divided by their own plan is 1 or more (100% achieved). Used by KPI 75.
    • direct_report_count: for each RM, the number of Active agents under them. For OH, AH, RH, VH and CH, the number of Active RMs under them. Used by KPI 63.

32. rrd_defence_sales_hist incremental, append

  • Copies the whole of rrd_defence_sales only when month_end_flag = 'Y'. On other days it adds nothing.
  • A pre_hook first deletes the hist rows for the current month, and only when the flag is 'Y'. A month-end re-run replaces that month. Earlier months are not touched.
  • Business impact: this is the record of each closed month. Dashboards that compare month to month read from here, so a missed month-end run leaves a gap.

Observations from the code

  1. YTD, QTD and 12-month rolling likely equal MTD. Every policy base model filters to month_id = curr_mth_id, so int_defence_sales_agent_agg receives one month only. Its YTD, QTD and rolling filters then have nothing extra to add. Meanwhile the YTD and QTD plans from the plan project are full-period totals. Business impact: YTD and QTD achievement % (KPIs 8, 13, 17, 28, 33, 37, 75) would show one month of actuals against a full-year or full-quarter target, so they would look far too low. KPIs 96 to 98 would show a single month, not 12. Please compare YTD and MTD for a few agents in real data to confirm.
  2. CRPF transfer rule may find nothing. rrd_defence_ceip_crpf_branch compares an agent's GO with the previous GO, but only loads the current month, so there is usually no previous GO. If so, the 'TBH' rule never fires.
  3. Fixed GO ADLU2. When the CRPF rule matches, the GO is always set to ADLU2, even if the agent's change involved ADGW2. The model's own comment says it should use the current GO from the CRPF list. The meaning of TBH is not defined in the code.
  4. Three KPIs differ from the STTM file. KPI 64 uses PAID_WPC (STTM says PAID). KPI 66 (ECS %) uses paid WPC policies, where STTM says APPLIED. KPI 95 (FYC) sums pol_fyc, where STTM says paid pol_mfyp. The mart's own comment on KPI 95 still says "paid mfyp". Please confirm which is intended, because these figures could feed incentives.
  5. Penetration ratios mix two marts. For example KPI 19 divides a PAID_WPC number by a PAID number. If the two marts disagree on a policy, a ratio can pass 100% or fall short.
  6. Net leakage adds the revived amount. KPI 88 = NPW + NTU + revived. If revived business should reduce leakage, it should be subtracted. This depends on the sign in the source. Please confirm.
  7. Case rate wording. The mart comment says the AH rate uses OHs under the AH. The code counts Active RMs for AH, RH, VH and CH, so the rate is policies per RM at every leader level.
  8. Policies can be dropped silently. The inner join to int_go_base removes any policy whose GO is not in the current hierarchy. No test or log reports how many were removed.
  9. Possible double counting. Several joins rely on one row per key but nothing enforces it: hierarchy_agency_all + hist (agent), the agent snapshot + hist, the CEIP adjustment full join (policy), and the surrender data (policy). A duplicate would multiply a policy's values.
  10. schema.yml is out of date. It says "114 KPI columns" (there are 148), it asks for uniqueness on (agent_id, month_id) although the table has three time_dimension rows per person, and it uses dbt_utils, which is not installed (there is no packages.yml). The hist description says it deduplicates, but it actually deletes the month and re-inserts.
  11. Unused objects. Models int_defence_sales_hierarchy_enrich and int_defence_sales_rm1_id, the macro union_current_hist, and three entries in sources.yml.
  12. Date macro risk. This project's get_date_vars() has no filter. Models cross join it, so if defence_date_master ever has more than one row, every number is multiplied by the row count.
  13. First run. The hist model's pre_hook deletes from its own table, so the very first run may fail until the table exists.

Staging layer

1. stg_defence_pol_lvl_preissuance and 2. stg_defence_pol_lvl_wpc table defence_int

  • What they do: keep only Defence policies from the pre-issuance and the WPC marts.
  • Logic: build a list of GO codes from the geo hierarchy table (current + hist, for the month in defence_date_master). Inner join the mart (hist and current, stacked with UNION ALL) to that list on wr_go_code = go_code. All source columns are kept.
  • No month filter here. Every month in the hist table is loaded. The month filter is applied later, in the MTD model.
  • Business impact: a policy written under a GO code that is not in the Defence hierarchy does not appear anywhere in this project.

3. stg_product_mapping, 4. stg_fct_sourcing_policy, 5. stg_dolphin_mapper, 6. stg_agent_master table

  • stg_product_mapping: product code and product name.
  • stg_fct_sourcing_policy: policy ID, journey, billing mode code (pol_bill_mode_cd), inforce date (pol_infc_dt) and policy-system status (pol_stat_ing).
  • stg_dolphin_mapper: joins the status mapping table to the proposal table on work status and sub status, drops deleted records (operation = 'D'), and returns proposal number (as pol_id) and the seller sub-milestone (as pol_status).

7. int_defence_pol_lvl_preissuance and 8. int_defence_pol_lvl_wpc table defence_int

  • Every join is a left join, so a policy is kept even if the plan name, status or agent record is missing.

9. int_defence_pol_lvl_unioned table

  • Stacks the two models above with UNION ALL. A source_system column says PRE_ISSUANCE or WPC. No aggregation.

Observations from the code

  1. QTD and YTD return no rows. Both models contain and 1=2. The mart therefore holds MTD rows only, although the documentation, the tests and the table design all describe three periods. Business impact: there is no quarter or fiscal-year policy list for drill-down. The row-count test compares the mart with the same empty models, so it does not notice.
  2. Only the AGENT level is active. The fan-out for RM, OH, AH, RH, VH and CH is commented out, but schema.yml says the table is replicated across seven levels. Business impact: a leader who filters on role_flag = 'OH' and their own ID gets nothing. They need to filter on the oh_id, ah_id and similar columns instead. Those columns are filled on every row.
  3. The documented table does not match the model. The model writes role_flag, reporting_id, def_kpi_70, def_kpi_209, master_flag and supervisor_id, none of which are in the table definition in DEFENCE DDL.txt. The same file stores payment frequency as a number, while the model writes text. Please check the deployed table, because a load can fail on a missing column.
  4. Hierarchy does not follow the scoreboard's CEIP rule. This project takes the reporting chain from the writing agent's own master record. The sales project moves CEIP policies to the campaign RM's office. A CEIP policy can therefore sit under a different RM and office here than in the scoreboard, so drill-down totals may not tie.
  5. Campaign code differs from the mapping file. The STTM file says KPI 70 should come from pol_journey in fct_sourcing_policy. The code takes campaignid from the marts. The staging model still loads pol_journey, unused.
  6. KPI 209 name. The STTM defines it as a Y/N flag for "Two-stage autopay". The code stores the raw initial method text under the name initial_payment_method. The Y/N flag is not produced, and KPI 207 is dropped before the mart.
  7. Possible duplicate policies. The Dolphin mapper does not keep one row per proposal. If a proposal has several work-status rows, its policy may be repeated. A policy that is in both pre-issuance and WPC in the same month also appears twice, with two stages. The union test only compares counts, so it does not catch this.
  8. Whole-number premiums. Premium columns are cast to numeric(18,0), which drops decimals.
  9. Stage can be blank. If the journey text matches no rule, stage and status are blank. The stage test may flag these rows.
  10. Loads every month. The staging models read all months from the hist tables and filter to the current month only at the MTD step. This costs run time as history grows. The staging models also select hist.* and curr.* and stack them by position, so both source tables must keep the same column order.
  11. Date macro risk. get_date_vars() has no filter. If defence_date_master ever has more than one row, models that cross join it return repeated rows.
  12. First run. The hist model's pre_hook deletes from its own table, so the very first run may fail until the table exists.

5. defence_health_data

Purpose. Builds the quality-of-business scoreboard for the Defence channel. The sales scoreboard (project 3) says how much was sold. This one says how much of it stays sold and how clean the selling was. For every person (Agent, RM, OH, AH, RH, VH, CH) it gives 26 KPIs in four groups:
  • Collection: premium expected from first-year policies against premium actually collected.
  • Persistency: share of premium still being paid at the 13th and 25th month.
  • Complaints and cancellations: grievance rate (GIR) and free look cancellation rate (FLC) per 10,000 policies.
  • Auto-pay (ECS): how many policies and how much collection comes through two-stage autopay.
Output table: defence_mart.rrd_defence_health (current month) and rrd_defence_health_hist (month-end snapshots, written by a post-hook).
Business impact. A policy that lapses after the first year or two means premium the company planned for never arrives. A rising complaint rate, mis-selling in particular, points to selling practice problems. Free look cancellations show policies returned just after sale. Leaders can see which teams sell business that stays, and the shortfall KPIs show how much unpaid premium sits behind a weak persistency figure.

Lineage

Models, one by one

A. People, offices and CEIP lists

1. int_defence_health_go_base table

  • What it does: the list of GO (office) codes with the leaders above them: OH, AH, RH, VH, CH, plus the offices of AH, RH and VH.
  • Logic: stacks the geo hierarchy table and its hist table (UNION), keeps rows where effective_month is the current month, and removes repeats with DISTINCT.
  • Business impact: it is also a gate. The persistency, FLC and GIR base models inner join to it, so data for a GO code that is not in the hierarchy is dropped from every KPI.

2. int_defence_health_hierarchy_base table

  • What it does: finds the RM of each agent (starting_id).
  • Logic: stacks hierarchy_agency_all and _hist (UNION ALL), keeps the current month, joins the designation setup on starting_desig = desig_code, and keeps only designations flagged RM. The design note says desig_desc, the code uses desig_code.
  • Business impact: decides whose RM total an agent's numbers go into.

3. int_defence_health_agent_master table

  • Current plus hist agent master for the month, with DISTINCT. It keeps 15 columns (ID, name, supervisor, GO, level, role, rm_id, rm1_id, oh to vh, zone). It does not keep ch_id, status or join date. This is the list of people who get a row in the final table.

4. int_defence_health_ceip_base table

  • Agents whose role is CEIP Agent in the agent snapshot (current + hist) for the current month. Output: agent ID and GO.

5. int_defence_health_ceip_adjustment table

  • Same logic as in the sales project. Policies from the CEIP adjustment dump (current + hist, current month) are full outer joined to rrd_denfence_ceip_mapping on policy number. A policy on either side is kept, and the dump's campaign wins when both have one.

6. int_defence_health_ceip_mapping table

  • What it does: for each CEIP policy, says which campaign RM and office it should be credited to.
  • Logic: takes each policy and its campaignid. campaignid_derived is TBH when that campaign ID is in the CRPF branch list, otherwise the campaign ID. It also carries the CRPF current and previous GO, and rm_go_code, the GO of the campaign agent when that agent is an RM in the agent master.

B. Policy, complaint and cancellation data

7. int_defence_persistency_base table

  • Grain: one row per policy for the current month.
  • Logic:
    1. Stack the persistency mart and its hist table with UNION ALL, each already filtered to the current month.
    2. Drop policies whose payment method is Single Premium, Payor Waiver or Premium Waiver. They have no repeat premiums to measure.
    3. Inner join to int_defence_health_go_base on the writing GO.
    4. ceip_flag = Y when the writing agent is in the CEIP agent list. Left join the CEIP mapping on policy ID for campaign, GO and RM GO.
    5. premium_mode: Annual 1, Semi-annual 2, Quarterly 4, Monthly 12. No later model uses this column.
    6. nop_payment_issue_dt: the number of payment cycles that should have fallen due from the issue date up to the end of the previous month. Monthly: months between the issue month and the current month. Quarterly and semi-annual: the months are counted from the start of the issue quarter or half-year, divided by 3 or 6, rounded up.
    7. nop_payment_due_dt: the number of cycles from the policy's current due date to the end of the previous month. This is the count of cycles still unpaid. It is 0 when the due date is after the end of the previous month. Same month, quarter and half-year rules.
  • Business impact: these two cycle counts drive the collection KPIs (38 to 41). Annual policies get no count (see observations).

8. int_defence_flc_base and 9. int_defence_gir_base table

  • Stack the FLC (or GIR) table with its hist table using the union_current_hist macro, keep the current month, and inner join to the GO base on wr_go_code.
  • FLC keeps flc_actual and ytd_gross_nop. GIR keeps total_grievance, misselling_grievance, service_grievance, ytd_paid_nop and ytd_paid_adj_mfyp.

Observations from the code

  1. The mapping sheet swaps KPI 42 and 43. final_data-ddl.txt says 42 is the numerator and 43 the denominator. The model, the business-logic note and the KPI names all say 42 (base) is the denominator and 43 (collection) the numerator. The model is probably right. Confirm and fix the sheet, because anyone building from the sheet would get persistency upside down.
  2. Depends on the sales project. The CEIP mapping and CRPF branch tables are built by defence_agent_sales and read here by source(). dbt does not enforce the order. If the sales project has not run yet, CEIP credit uses the previous run's lists.
  3. CEIP credit is applied unevenly. In int_persistency_agg the GO is replaced by the campaign RM's GO for any policy on the CEIP list, but the RM is replaced only when the writing agent is a CEIP agent. A non-CEIP agent's policy can end up with the campaign RM's office and its own RM. The RM is the raw campaign ID here, while the sales project uses TBH for CRPF cases. FLC and GIR have no CEIP logic at all, so for the same RM and office the persistency, complaint and cancellation figures may cover different people. The fixed GO ADLU2 has the same issue as in the sales project.
  4. Annual policies are left out of the collection KPIs. The cycle count has branches for monthly, quarterly and semi-annual only. For an annual policy it is null, so its premium is missing from the collection target and actual (KPIs 38 to 41). Business impact: collection looks lower or higher than it is, depending on how many annual policies a team has.
  5. ECS % uses a wider denominator. KPIs 298 and 300 divide 13M (or 25M) auto-pay policies by all policies of the person, across every block. They are not "share of 13M policies on auto-pay". The percentage is understated.
  6. Collection target differs from the design note. The note multiplies by premium_mode / 12. The code does not. The premium_mode column is built and never used. The code's version may well be the right one, since cycles are already counted, but the note should be updated.
  7. KPI 39 is named "rolling 12 month". The formula covers policies aged 1 to 12 months, not a rolling 12-month window of collections. Please confirm the intended meaning.
  8. Thresholds are fixed in code. 84% in KPIs 45 and 49, and 0.92 in KPIs 91 and 93. KPIs 91 and 93 go negative above the target, and KPIs 45 and 49 are zero above 84%, so a team at 90% shows no shortfall in KPI 45 but a positive one in KPI 91.
  9. History is written by raw SQL. The post-hook INSERT ... SELECT * has no column list, so the hist table must have the same columns in the same order. The first month-end run fails if the table does not exist. The pre-hook deletes all rows, although the design note says only the current month.

Observations from the code

  1. Depends on three projects. The agent master, the plan tables and the sales scoreboard are all read with source(), so dbt does not enforce the order. If this project runs first, every KPI uses last run's data.
  2. No agent-level rows. The part of int_rrd_defence_dsc_kpi_bsc that outputs agent rows is commented out. The mart holds only RM, OH, AH, RH, VH and CH rows. The design documents say the table has one row per agent. Business impact: nobody can see the BSC of an individual agent.
  3. Eight of 24 KPIs are always empty. KPIs 197, 199, 208, 304 and 311 have no source. KPIs 198 and 305 divide by them, so they are empty too. KPI 310 (agent recruitment) is calculated in the agent model, but the final column is set to null, so the count never reaches the table. Business impact: lecture, lead and agent-recruitment tracking is not available from this table.
  4. Attrition (KPI 284) is combined as text. The values look like 20%, and the rollup takes the MAX of those strings, which sorts alphabetically: 9% counts as higher than 10%. The mapping file says attrition is meant for people with level RH only. The code attaches it to everyone with a staff code and the rollup shows the worst value, not an average (the column is called avg_284). Business impact: a leader's attrition figure can be wrong, and can be the wrong kind of number.
  5. Plan KPIs use MAX, the percentage uses SUM. For KPIs 196 and 303, a leader's row shows the largest plan of the people under them. The comment says "SUM". The percentage KPIs 198 and 305 use the sum. When each agent has their own plan, the plan shown is far lower than the plan used in the percentage. When the office plan is copied to every agent in the same office, MAX is correct and SUM would double count. The correct rule depends on which plan applies, and the code does not tell them apart.
  6. URN (KPI 202) shows one office only. The count is per GO, and a leader with several offices gets the MAX, not the total. The count has no month filter. The comments and sources.yml point to a different table (rrd_defence_urn_temp) than the one the code reads.
  7. QTD and YTD only partly make sense. Recruitment and new-activization counts use the join month only, so QTD and YTD rows repeat the monthly count. Activization uses the period's paid NOP from the sales scoreboard, which (see project 3) likely equals the month for QTD and YTD.
  8. Contribution KPIs differ from the mapping file. The mapping file divides by the Channel Head total. The code divides by the team's own AGT + RKO total, so the agent and RO shares always add to 100% and anyone who is neither AGT nor RKO (for example RMs) is left out. The comment at the top of int_..._kpi_bsc still says "CH total". The channel totals are calculated and not used.
  9. Who is shown at which level. Anyone who is also an OH, AH, RH or VH is dropped from the lower levels so they are not shown twice. A person who is both an RM and an OH therefore has no RM row. The CH row sums the whole channel, and its ID comes from the person with level CH. If none exists, the ID is blank.
  10. Plan tables are read without history. The two intermediate models read the current plan tables directly. The geo plan is joined on office and period only, without the month. The staging views that combine current and hist (with the month filter) are used only by a test. A back-run for an older month can lose plan figures or pick up several months.
  11. Truncate before load. The mart's pre_hook runs truncate table. In Redshift a truncate commits straight away, so if the load then fails, the table stays empty until the next good run.
  12. Tests do not fit the mart. assert_activization_binary requires KPIs 281 to 283 to be 0 or 1, but on leader rows they are counts, so the test will fail. assert_lecture_plan_routing expects an RM's plan to equal the RM's own producer plan, but the RM row shows the MAX of the team. Also unused: stg_..._field_plan_* (except in that test), three entries in sources.yml, and a comment saying run_flag = 'Y'.
  13. Date macro risk. get_date_vars() has no filter and no LIMIT. If defence_date_master ever has more than one row, models that cross join it return repeated rows.

7. defence_go_ho_movment

Purpose. Tracks who has to act on policies that are stuck before issue. A policy in WIP (being processed) or Hub Hold (held at the hub) always waits for someone. The project sorts every such policy into a GO bucket (the branch or seller side must act) or an HO bucket (the head office side must act), and then measures, for each office and each leader, how much of that waiting business is new today and how much has been waiting.

KPIs created: 8, in two pairs for each of WIP and Hub Hold: GO and HO, counted by number of policies (NOP) and by adjusted AFYP.
Output table: defence_mart.rrd_defence_go_ho_mvmt (rows for the current day, labelled FTD, and for the month so far, labelled MTD) and rrd_defence_go_ho_mvmt_hist (month-end snapshot of the MTD rows).
Business impact. Business stuck in WIP or Hub Hold is premium that is not yet earned. If most of it sits in the GO bucket, branches and sellers must chase customers and documents. If it sits in the HO bucket, head office operations must clear it. These KPIs let a leader see which side holds the delay and which offices carry it. The page flags two problems that decide whether the Hub Hold figures can be trusted: they come out as 100% by construction, and the "next day" status may be missing on the day the report runs.

  • Logic: inner join to the GO list on the writing office, and keep rows whose as_on_date is in the month of the reporting date. Columns are renamed to a common layout: agent ID, GO code, policy ID, adjusted AFYP, ageing text, actionable reason, bucket, and a source label (WIP or HUB_HOLD).
  • Hub Hold differences: the actionable column is renamed to the WIP name, and the ageing text is set to null, because Hub Hold has no ageing in its source.
  • Business impact: a policy written under a GO code that is not in the Defence list never appears in the KPIs.

4. stg_rrd_defence_go_ho_combined table

  • WIP and Hub Hold stacked with UNION ALL, spread across servers by policy ID and sorted by date, so the self-join in the next models runs faster. The two inputs must have the same columns in the same order.

6. int_rrd_defence_go_ho_flags table

  • What it does: adds three columns by comparing each policy-day (D1) with the same policy on the next day (D2). Both days come from the month's data. The join is on policy ID, source and date plus one day.
  • ftd_flag: FTD when D1's ageing is 0, otherwise Others.
  • latest_status: D2's GO / HO bucket. When the policy has no row the next day, it is set to HO.
  • latest_ftd_flag: whether D2's ageing is 0 (FTD), or Others when there is no next-day row. No later model uses this column.
  • Business impact: this is the heart of the project. Whether a policy counts under GO or HO depends on its bucket tomorrow, and a policy that leaves the queue (issued, cancelled) is counted as HO.

7. int_rrd_defence_go_ho_ftd incremental

  • Grain: one row per policy per day per source. Unique key: policy ID, date and source.
  • What it does: the persistent daily snapshot. Each run adds only the reporting day's rows from the flags model. A re-run of the same day replaces that day.
  • Month change: when the month in the table is not the reporting month, the whole table is emptied first (DELETE FROM), so it only ever holds one month.
  • A variable run_ftd = false makes the model add nothing.

8. int_rrd_defence_go_ho_mtd table

  • Grain: one row per GO, month and source.
  • What it does: reads every day stored in the daily table for the month and counts, per GO and source, the pieces that go into the month-to-date KPIs. Counts are policy-days (see terms). The numerator and denominator rules are in the next section.
  • There is no month-end gate. It runs every time.

Intermediate layer: KPI building blocks

9. int_rrd_defence_go_ho_wip_kpi and 10. int_rrd_defence_go_ho_hub_kpi table

  • Each produces two kinds of rows per GO: FTD rows from the reporting day's snapshot in the daily table, and MTD rows copied from the month-to-date model. Each row holds eight counts: for GO and for HO, the number and AFYP numerator and denominator.
  • The two models have exactly the same formulas. They differ only in the source filter (WIP or HUB_HOLD). The header comment of the Hub Hold model says its signal is "next-day bucket differs from today", but the formula uses the FTD flag, as in WIP.

11. int_rrd_defence_go_ho_combined_kpi table

  • Puts the WIP and Hub Hold counts side by side in one row per GO, month and period (FULL OUTER JOIN). A missing side becomes 0.

Intermediate layer: reporting chain

12. int_rrd_defence_go_ho_agent_master table

  • The people list for the month from the agent master and its hist table (UNION): ID, name, level, role, supervisor, GO, zone and OH to CH IDs. All levels are kept, so each level can look up its own details.

13. int_rrd_defence_go_ho_base_kpi table

  • Joins the combined counts to the chain of leaders above each GO. For each GO it takes the agent master rows with level OH and uses MAX() of their IDs, so if one GO has two OH rows only one is used.
  • This model exists so the join runs once and not five times, one for each leader level.

Mart layer

15. rrd_defence_go_ho_mvmt incremental defence_mart

  • Grain: one row per leader (and per GO for OH), per period (FTD or MTD).

How to read a KPI. For WIP: among the policies whose next-day bucket is GO, the share that arrived today (ageing of 0 days). A high value means the GO bucket is filling with fresh cases. Counting. For the day, counts are of distinct policies. For the month, the code counts rows (policy-days), so a policy that waits five days adds five to the denominator.

Business impact. A rising share of new arrivals in the GO bucket points to new work reaching branches faster than they clear it. A low share points to a backlog. The business wording in the mapping file ("movement") suggests a measure of cases that moved between buckets. The formula does not compare today's bucket with tomorrow's, so please confirm which meaning is wanted before leaders act on these numbers (see observation 3).

Observations from the code

  1. Hub Hold KPIs 317 to 320 come out as 100% or 0. The Hub Hold source has no ageing, so the model sets ageing to 0 for every Hub Hold row. That makes every row an FTD row, so the numerator (FTD and GO) always equals the denominator (GO). Each KPI is therefore 1 where there is any policy and 0 where there is none. The mapping file describes a different flag for Hub Hold, "moved or not moved", based on whether the policy was in the previous day's data. Business impact: four of the eight KPIs carry no information today.
  2. "Latest status" needs the next day's data. Each policy's bucket is read from the following day, and a policy with no row the next day is counted as HO. On the day being processed there is normally no next day yet, and on the last day of the month there never is. Those rows then all become HO. The daily table adds only the reporting day, so a day's row is not corrected when the next day arrives. A policy that leaves WIP (issued or cancelled) is also counted as HO. Business impact: the GO KPIs can be empty and the HO KPIs inflated for the latest day. Please check what the next-day data looks like at run time. The requirement document describes the opposite direction: the status of the previous day, and NA when missing.
  3. The KPIs measure arrival share, not movement. The formula divides "new today in this bucket" by "in this bucket tomorrow". It does not compare buckets between days. The mapping file talks about movement and the mvmt.yml file says the KPI is "(FTD count / Total count) * 100". The code returns a fraction between 0 and 1, not a percentage. Please confirm the meaning and the scale.
  4. Missing ageing text counts as "Others", not "FTD". The comment says a missing or unmatched ageing becomes 0. The code leaves it null, and null is not equal to 0, so the policy is Others. The text must also start with digits followed by the capital word DAYS (for example 0DAYS). A text like 0 Days is not matched. The not-null test on this column in the yml file would fail for such rows.
  5. OH rows are per office, and some have a blank ID. One OH row is written for each GO, so an OH with three offices has three rows with the same agent_id. A user who sums the rows gets the correct total, but one who reads a single row gets only one office. If a GO has no OH in the agent master, its row has a blank agent_id and no chain, and its numbers are left out of AH, RH, VH and CH totals. If a GO has more than one OH row, only one (the highest ID) is used.
  6. The month is built one day at a time. The daily table gets one day per run, and it is emptied when the month changes. A day that was not run is missing from the month-to-date numbers until it is re-run. The back-fill script has the dates typed in (April 2026, days 1 to 30) and has to be edited each time. A single run at month start produces month-to-date numbers from one day only.
  7. History keeps month-end MTD rows only. The mart is emptied on each run, and the daily table is emptied at the start of a new month. If the month-end run is missed, or the flag is not Y that day, the month's final figures are lost. The hist table has no FTD rows, so the daily figures are not kept.
  8. Month-to-date and daily counts differ. The daily rows count distinct policies. The month-to-date rows count rows, so a policy listed twice on the same day in the source is counted twice.
  9. Tests and documents do not match the code. test_mtd_gte_ftd_nop.sql reads a column source_table_flag from the mart, and the mart has no such column, so the test fails when it runs. The mart yml uses dbt_utils, which is not installed (no packages.yml), and its unique key includes go_code, so it would not catch a repeated OH row. The yml for the flags model describes a previous-day LAG, while the code looks at the next day. The Python tests use different actionable values (SELLER, CUSTOMER WIP) than the SQL (SELLER / CUSTOMER WIP), and they check Python copies of the rules, not the database.
  10. The default reporting date is read when dbt starts. dbt_project.yml sets the variable to {{ get_reporting_date() }}, which runs a query against the date master. Whether dbt can run a macro there depends on the version, because project settings are read before macros are loaded. Please confirm that a plain dbt run picks the right date and does not fall back to 1900-01-01. If it does, all data filters return nothing.
  11. A zero denominator shows as 0. The mart returns 0 when there are no policies, so "no policies in this bucket" cannot be told apart from "none of them is new". Null would be clearer.
  12. The GO / HO mapping is written into the SQL. A new actionable reason that is not in the list is treated as HO without any warning. A change needs a code change.
  13. Unused or stale items. The macro get_date_vars, the variable force_mtd, the column latest_ftd_flag, the backup script dbt_run_loop - BKP.sh (which has a different date and targets the mart models only), and the commented-out ch_id in the mart. The mart and hist pre_hook run DELETE FROM on their own table, so the very first run fails until the tables exist.
